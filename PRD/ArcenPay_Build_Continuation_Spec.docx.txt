02 — Authentication & Identity Layer
There is zero auth in the current build. Every dashboard page, every API endpoint, and every SDK hook assumes an identity that doesn't exist yet. This section defines the complete auth stack.


2.1 Sign-In With Ethereum (SIWE)
The protocol must never store passwords or emails. Identity is a wallet signature. SIWE (EIP-4361) is the standard — the user signs a structured message with their wallet, and the server verifies the signature to issue a session.


2.1.1 Provider Dashboard Auth Flow
1. User visits dashboard → Wagmi detects no wallet session → redirect to /login
2. /login renders ConnectWallet button (Wagmi + WalletConnect modal)
3. On wallet connect: fetch nonce from GET /auth/nonce (server-generated, stored in Redis/DB)
4. Client constructs SIWE message with nonce, domain, chainId, address, issuedAt
5. User signs message via wallet — no gas, no transaction
6. Client POSTs { message, signature } to POST /auth/verify
7. Server: ethers.verifyMessage(message, signature) → recover signer address
8. If recovered address matches claimed address + nonce is valid: issue JWT (HS256) + HttpOnly session cookie
9. JWT payload: { address, chainId, planIds[], isProvider: bool, exp }
10. All dashboard API routes protected by verifyJWT middleware


2.1.2 SDK Consumer Auth (useEntitlement Hook)
End-users of apps built on ArcenPay don't log in to a dashboard — their wallet IS their identity. The useEntitlement hook must:
* Read the connected wallet address from Wagmi's useAccount()
* Call SubscriptionRegistry.isValid(tokenId) + SubscriptionRegistry.expiresAt(tokenId) via viem readContract
* Cache result with TanStack Query (staleTime: 30s, refetch on block number change)
* Subscribe to SubscriptionRegistry Transfer and Renewed events to invalidate cache on-chain state change


2.1.3 Facilitator Node Auth (x402 Payment Verification)
The facilitator must authenticate incoming X-PAYMENT headers. Current implementation is a stub with no actual validation. Required:
* Parse X-PAYMENT header: base64-decode → JSON { signature, payload, chainId }
* Recover signer from EIP-712 typed data signature (viem's recoverTypedDataAddress)
* Verify: signer has sufficient session vault balance (readContract SessionVault.balanceOf)
* Verify: payment amount matches x402 payload's maxAmountRequired
* Submit on-chain: writeContract FeeCollector.collectPayment({ from, to, amount, sessionId })
* Return 402 with WWW-Authenticate: x402 on failure; call next() with enriched req.user on success

* On-chain: uninstall removes executor from kernel's module list — billing contract loses call authority immediately
* Provider dashboard: subscription shows 'Cancellation Pending' until current period expires

05 — Lit Protocol MPC Access Control
This is MEAP's cryptographic access control layer. Without it, FeatureFlagGuard is a simple client-side check that any user can bypass. With Lit Protocol, access is enforced by a decentralized MPC network.


5.1 Integration Setup
* Install: @lit-protocol/lit-node-client, @lit-protocol/constants, @lit-protocol/auth-helpers
* Network: Manzano (testnet) → Habanero (mainnet) — set via MEAPProvider litNetworkConfig
* Initialize LitNodeClient once in MEAPProvider, expose via useLit() hook


5.2 Access Control Condition (ACC) Structure
Each feature flag maps to an ACC. The ACC checks two things in AND-conjunction:
* Condition 1: SubscriptionRegistry.isValid(tokenId) returns true for the user's wallet
* Condition 2: Tableland query returns feature_flags JSON containing { [featureKey]: true } for the wallet


⬡  ACC JSON Structure Example
accessControlConditions: [
  {
    contractAddress: SUBSCRIPTION_REGISTRY_ADDRESS,
    standardContractType: 'ERC721',
    chain: 'base',
    method: 'isValid',
    parameters: [':userAddress'],  // resolved at eval time
    returnValueTest: { comparator: '=', value: 'true' }
  },
  { operator: 'and' },
  {  // Tableland read via Lit action
    conditionType: 'evmBasic',
    contractAddress: TABLELAND_TABLE_ADDRESS,
    method: 'getFeatureFlag',
    parameters: [':userAddress', featureKey],
    returnValueTest: { comparator: '=', value: 'true' }
  }
]
	

5.3 FeatureFlagGuard Implementation
The FeatureFlagGuard component must use Lit Protocol to request a decryption key, not just check a contract boolean. This ensures the access decision is made by the Lit node network.
* On mount: call litNodeClient.getSessionSigs({ chain, resourceAbilityRequests }) to get session signatures
* Call litNodeClient.getEncryptionKey({ accessControlConditions, toDecrypt: encryptedKey, chain, sessionSigs })
* If key is returned: decrypt the feature payload and render {children}
* If key is not returned (ACC failed): render {fallback}
* Cache session sigs with 24h TTL — don't call Lit on every render
* Latency target: < 200ms p95 (Lit Chronicle Yellowstone nodes are fast — test and verify)


5.4 Encryption Key Management
Providers need a way to encrypt their feature-gated content. Add meap.encryptContent(content, accessControlConditions) to @meap/node SDK.
* Server-side: LitNodeClient.encrypt({ dataToEncrypt, accessControlConditions }) → { ciphertext, dataToEncryptHash }
* Store ciphertext in your app's database or IPFS — never the plaintext
* Store dataToEncryptHash in Tableland alongside the feature flag record

07 — ZKVUB: x402 + zk-SNARK Pipeline
The ZKVUB subsystem is the most technically complex remaining work. Build it in three sequential phases — do not attempt zk-proof generation before x402 validation is solid.


7.1 Phase A — x402 Signature Validation (Do This First)
The current facilitator returns HTTP 402 but does not validate the X-PAYMENT header. This must be fixed before anything else in ZKVUB.


7.1.1 X-PAYMENT Header Validation Algorithm
11. Parse header: const payment = JSON.parse(Buffer.from(xPaymentHeader, 'base64').toString())
12. Verify EIP-712 signature: const signer = await recoverTypedDataAddress({ domain, types, primaryType: 'Payment', message: payment.payload, signature: payment.signature })
13. Check signer matches payment.payload.from address
14. Verify payment.payload.resource matches requested URL
15. Verify payment.payload.maxAmountRequired >= endpoint's configured rate
16. Check session vault balance: const balance = await publicClient.readContract({ address: SESSION_VAULT, abi, functionName: 'balanceOf', args: [signer] })
17. If balance < maxAmountRequired: return 402 with { error: 'Insufficient session balance' }
18. Submit on-chain: await walletClient.writeContract({ functionName: 'recordPayment', args: [signer, amount, sessionId] })
19. Log usage: append { sessionId, agentAddress, timestamp, endpoint, callData } to in-memory log (append to Merkle tree leaf list)
20. Return 200 with X-PAYMENT-RESPONSE header containing txHash


7.2 Phase B — Off-Chain Aggregation Service
Build a standalone aggregator service that runs alongside the facilitator. This is NOT part of the Express app — it's a separate Node.js process or cron job.


7.2.1 Aggregator Architecture
* Process: Long-running Node.js service subscribed to facilitator's usage log stream
* Data structure: MerkleTree of keccak256(sessionId + timestamp + callCount + agentAddress) leaf hashes
* Triggers: Flush proof generation when (A) time window closes (default: 1 hour) OR (B) session call count > threshold (default: 10,000)
* Storage: Redis sorted set per sessionId — score = timestamp, value = signed usage log JSON
* Output: { sessionId, agentAddress, callCount, windowStart, windowEnd, merkleRoot, leaves[] }


7.2.2 Consumption Log Signing
Every usage event must be signed by the facilitator's server wallet to prevent tampering:
* Facilitator signs: keccak256(abi.encode(sessionId, agentAddress, endpoint, timestamp, callIndex))
* Signature stored alongside usage log entry in Redis
* zk-SNARK circuit verifies all signatures are from the facilitator's known public key


7.3 Phase C — zk-SNARK Circuit (Circom)
This is the most specialized work in the entire protocol. Budget 3–4 weeks for a developer experienced with Circom. If no one on the team has ZK experience, this is the place to hire a specialist or use Sindri.


⬡  Circuit Inputs (Public & Private)
Public inputs:  agentAddress, sessionId, callCount, windowStart, windowEnd, merkleRoot, nullifier
Private inputs: usageLogs[] (array of { timestamp, endpoint, signature }), merkleProofs[]


Circuit constraints:
1. For each usageLog: verify facilitatorSig is valid ECDSA over keccak(sessionId, agentAddress, timestamp)
2. For each usageLog: compute leaf = keccak(sessionId, timestamp, agentAddress, index)
3. All leaves form valid Merkle tree with root == merkleRoot (public input)
4. callCount == count(usageLogs) (no fabrication, no omission)
5. All timestamps: windowStart <= timestamp <= windowEnd
6. nullifier == keccak(sessionId, windowEnd) (prevents reuse)
	

7.3.1 Circuit Implementation Files
* circuits/UsageBilling.circom — main circuit
* circuits/lib/MerkleProof.circom — reuse from circomlib
* circuits/lib/ECDSAVerify.circom — use circom-ecdsa library
* circuits/UsageBilling.test.ts — full test suite with snarkjs
* scripts/setup.sh — Powers of Tau ceremony + circuit-specific setup
* scripts/prove.ts — Generate proof from witness (called by aggregator)
* scripts/export-verifier.sh — Export Solidity verifier (update ZKUsageVerifier.sol)


7.3.2 Proving Pipeline Integration
* Aggregator calls prove.ts with JSON witness → Groth16 proof + publicSignals
* meap.submitProof(proof, publicSignals) → writeContract ZKUsageVerifier.submitProof()
* Target: < 30 seconds proof generation for 100k call windows (run prover on GPU-enabled server)
* Consider Sindri API for managed proving infrastructure — avoids GPU server overhead

08 — Cross-Chain GMP Integration (Axelar)


8.1 Axelar Integration in SubscriptionRegistry.sol
After each successful billing event, the SubscriptionRegistry must dispatch a GMP message to update MirrorRegistry contracts on all other chains. This requires modifying the existing contract.


⬡  Contract Modification Required
In SubscriptionRegistry.sol — add Axelar IAxelarGateway and IAxelarGasService imports.
In renew() and mint(): After state update, call:
  bytes memory payload = abi.encode(tokenId, newExpiresAt, planTier);
  gasService.payNativeGasForContractCall{value: gasFee}(address(this), destinationChain, mirrorAddress, payload, refundAddress);
  gateway.callContract(destinationChain, mirrorAddress, payload);
Do this for each chain in the provider's registered chainIds[].
	

8.2 MirrorRegistry.sol — execute() Handler
MirrorRegistry.sol must implement IAxelarExecutable. The execute() function is called by the Axelar gateway when a message arrives:
* Validate: msg.sender == axelarGateway address (CRITICAL — do not skip)
* Validate: sourceChain and sourceAddress match registered SubscriptionRegistry
* Decode payload: (tokenId, expiresAt, planTier)
* Update: mirrorState[tokenId] = { expiresAt, planTier, lastSynced: block.timestamp }
* Emit: EntitlementSynced(tokenId, sourceChain, expiresAt)


8.3 GMP Cost Management
Axelar GMP calls are not free. Gas estimation and cost management must be built in:
* Use Axelar's AxelarQueryAPI to estimate gas fees per destination chain
* Provider must pre-fund the GMP gas in the SubscriptionRegistry contract (native token)
* Add Dashboard → Settings → 'GMP Gas Balance' with top-up functionality
* Alert when GMP gas balance < 3 billing cycles worth of estimated fees

9.2 Email Notifications (Transactional)

* Integration: Resend or SendGrid — provider adds their own API key in Dashboard → Settings → Notifications
* Subscriber email linking: Optional — subscriber provides email address during CheckoutModal (stored encrypted off-chain, never on-chain)
* Email templates required: Welcome, Renewal Receipt, Payment Failed, Subscription Expiring (3 days before), Access Revoked, Low Session Balance
* All templates must be customizable with provider branding via Dashboard → Settings → Email Templates


9.3 Provider Webhook System
Every billing event must be POSTable to a provider-configured webhook URL. This is how providers integrate with their existing backend systems.
* Dashboard → Settings → Webhooks: add endpoint URL + signing secret
* Payload format: { event: 'subscription.renewed', timestamp, data: { tokenId, address, planId, amount, txHash } }
* Signing: HMAC-SHA256(payload, signingSecret) sent as X-MEAP-Signature header (Stripe-style)
* Retry policy: Exponential backoff — 1s, 5s, 30s, 5min, 30min. Max 5 retries.
* Dashboard: Webhook delivery log with response codes + replay button


9.4 Push Notifications (Future / Wallet-Native)
For a fully decentralized notification layer, integrate XMTP or Push Protocol. This is Phase 2 — implement after email/webhook system is stable.
* XMTP: wallet-to-wallet encrypted messaging — facilitator sends XMTP message to subscriber wallet on billing events
* Push Protocol: On-chain notification channels — subscriber opts in to ArcenPay channel

* Danger Zone: emergency pause (if PauserRole implemented), protocol fee settings


10.2 The Graph Indexer (Critical for Dashboard Data)
Reading historical event data directly from RPC is slow and unreliable. The dashboard needs an indexed data source. Build a subgraph.
* Install: @graphprotocol/graph-cli, @graphprotocol/graph-ts
* Subgraph entities: Provider, Plan, Subscriber, BillingEvent, Session, ProofSubmission
* Index events from: PlanFactory, SubscriptionRegistry, ZKUsageVerifier, SessionVault, FeeCollector
* Deploy to The Graph Studio (hosted service) for testnet; decentralized network for mainnet
* SDK integration: replace direct event queries with GraphQL queries via @apollo/client or urql

11 — Facilitator Node: Production Hardening


11.1 Docker Image
The facilitator must be distributable as a Docker image so providers can self-host it. The current Express app is not Dockerized.
* Create apps/facilitator/Dockerfile — multi-stage build (node:20-alpine)
* Environment variables: PRIVATE_KEY, RPC_URL, SESSION_VAULT_ADDRESS, PLAN_FACTORY_ADDRESS, REDIS_URL, PORT
* Create docker-compose.yml in root: services for facilitator, redis, aggregator
* Health check endpoint /health must return { status: 'ok', blockNumber, chainId }
* Publish to Docker Hub as arcenpay/facilitator:latest


11.2 Rate Limiting & DDoS Protection
* Per-IP rate limit on /api/* routes: 100 req/min (express-rate-limit)
* Per-wallet rate limit on x402 endpoints: configurable per plan tier
* Request size limit: 50KB body limit to prevent payload attacks
* CORS: whitelist provider's configured domains only


11.3 Facilitator Wallet Security
The facilitator uses a hot wallet (PRIVATE_KEY env var) for on-chain submissions. This is a security risk that must be managed.
* Short-term: PRIVATE_KEY in environment variables + Doppler/Vault for secrets management
* Recommended: Use AWS KMS or HashiCorp Vault for key storage — never plaintext PRIVATE_KEY in .env files
* Limit facilitator wallet's on-chain permissions to ONLY the operations it needs (FeeCollector.record, SessionVault.debit)
* Set maximum transaction value limit in contract — facilitator wallet cannot spend more than X USDC per tx

12.1 GitHub Actions Pipelines

	facilitator.yml

	release.yml
	Changesets version bump → npm publish @meap/* packages → GitHub Release
	

12.2 Contract Testing Requirements
Current Foundry tests cover basic happy paths. Production requires adversarial test coverage.
* Fuzz testing: forge fuzz on all write functions with random inputs (run 10,000 iterations minimum)
* Invariant testing: forge invariant — key invariants: totalSupply == mintCount - burnCount, allActiveNFTs have expiresAt > block.timestamp, noModuleCanPullMoreThanMaxAmount
* Reentrancy tests: mock malicious ERC20 that tries to reenter on transferFrom
* Access control tests: assert every privileged function reverts when called by non-owner
* Fork tests: run tests against forked Base mainnet state (forge test --fork-url)


12.3 Pre-Audit Checklist
Before engaging a formal security audit, complete these internal reviews:
* Slither: zero high/medium findings in slither output
* Mythril: run MythX analysis on all contracts
* Manual review: trace every external call for reentrancy, check all arithmetic for overflow
* Invariant documentation: write a INVARIANTS.md explaining all assumed protocol invariants
* Emergency mechanisms: implement pause() with OpenZeppelin Pausable on billing-critical contracts
* Audit firm selection: Trail of Bits, Spearbit, or Cantina — begin outreach at 80% feature completion


12.4 SDK Testing
* Unit tests for every @meap/sdk-core utility function
* Integration tests for @meap/sdk-node: mock viem publicClient + walletClient, test all contract interactions
* React component tests: @testing-library/react for all 7 SDK components with wagmi test utils
* E2E tests: Playwright against local Anvil fork — test complete CheckoutModal flow

16 — Small Things That Add Up to Production-Quality
Every production system has dozens of small details that aren't in any spec but matter for real-world use. These are easy to miss.


16.1 UX Polish Checklist
* All wallet addresses: truncate to 0x1234...5678 format everywhere, full address on hover with copy-to-clipboard
* All transaction hashes: clickable links to appropriate block explorer (BaseScan for Base, Etherscan for Sepolia)
* All amounts: display in human-readable USDC (divide by 1e6), show full atomic amount on hover
* All timestamps: display in user's local timezone with relative time ('2 days ago') + absolute on hover
* Empty states: every table/list must have a designed empty state (not just 'No data found')
* Loading states: skeleton loaders for all contract reads — never blank white space while loading
* Error boundaries: React ErrorBoundary around all contract-dependent UI sections
* Responsive design: dashboard must work on tablet (1024px) — not just desktop


16.2 SDK Developer Experience
* TypeScript: strict mode enabled, all functions fully typed with JSDoc comments
* Error classes: throw typed errors (MEAPError, ContractError, LitError) with descriptive messages
* Changelog: use Changesets for automated changelog generation on every release
* README: each SDK package needs a 5-minute quickstart README with copy-pasteable code
* Storybook: all 7 React components documented with interactive stories
* npm publish: configure @meap/* scope, automate via GitHub Actions on version tag


16.3 Security Hygiene
* Never log private keys, wallet addresses, or payment payload contents in production logs
* All API responses: strip internal stack traces before sending to client
* Input validation: use zod schema validation on all API request bodies
* Dependency audit: run npm audit weekly via GitHub Actions dependabot
* Rate limit all auth endpoints: POST /auth/verify max 10/min per IP
* CORS: configure strict origin allowlist — never Access-Control-Allow-Origin: *


16.4 Operational Readiness
* Runbook: write runbook for common operational scenarios (proof stuck, GMP message delayed, facilitator down)
* Incident response: define severity levels and response procedures
* Backup: Redis data backup every 6 hours (usage logs are valuable — loss = unbillable usage)
* DB migrations: use prisma migrate or Atlas for any relational DB schema changes — no manual DDL
* Staging environment: maintain staging deployment on Base Sepolia that mirrors production config

17 — Open Architecture Decisions
These decisions need to be made before or during the build. Deferring them too long will cause expensive rework.


Decision
	Options
	Recommendation
	Proving infrastructure for zk-SNARK
	Self-hosted GPU prover vs. Sindri managed API vs. Risczero
	Sindri for MVP — avoids GPU server ops. Self-host at scale.
	Off-chain data store (non-Tableland)
	PostgreSQL vs. PlanetScale vs. Supabase
	Supabase — real-time subscriptions useful for event streaming
	Agent SDK auth for autonomous agents
	ECDSA private key vs. Turnkey MPC vs. Privy server wallets
	Turnkey — non-custodial, API-accessible, no raw private key
	Multi-sig checkout for DAOs
	Safe{Wallet} SDK vs. custom transaction builder
	Safe SDK — largest DAO adoption, best tooling
	GMP provider fallback
	Axelar only vs. Axelar + CCIP dual routing
	Dual routing — CCIP as fallback if Axelar is congested
	Dashboard auth (alternative to SIWE)
	SIWE only vs. SIWE + Privy embedded wallets
	SIWE only for MVP — Privy adds complexity and cost
	Contract upgrade strategy
	Immutable vs. OpenZeppelin Proxy (UUPS)
	UUPS Proxy on all contracts pre-audit. Immutable post-audit.
