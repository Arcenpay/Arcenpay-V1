01  EXECUTIVE SUMMARY & PRODUCT VISION
	

What We Are Building
The Web3 Entitlement Layer is a foundational, open protocol that unifies on-chain automated payment execution with cryptographic feature access control. It is the decentralized equivalent of what SchematicHQ + Stripe + LaunchDarkly provide in the Web2 world — but natively architected for wallets, DAOs, AI agents, and multi-chain environments.
The protocol comprises two interconnected subsystems:
* MEAP (Modular Entitlement and Access Protocol): Handles automated recurring billing and cryptographic feature gating for human users and DAOs using ERC-7579 smart accounts and Lit Protocol threshold cryptography.
* ZKVUB (Zero-Knowledge Verifiable Usage Billing Network): Handles metered, usage-based billing for AI agents and machine-to-machine commerce using the x402 payment standard and zk-SNARK proofs for trustless settlement.


The Core Problem
Current SaaS billing infrastructure is structurally incompatible with the decentralized web. Three irresolvable gaps exist:
1. EOA Automation Bottleneck: Standard crypto wallets (EOAs) cannot execute automated recurring payments. Every transaction requires manual user signing, making subscription commerce impossible without centralized workarounds.
2. Multi-Chain State Fragmentation: A subscription purchased on one blockchain network is invisible to contracts on another. There is no native, trustless mechanism to synchronize entitlement state across isolated Layer 1 and Layer 2 networks.
3. The Trust Deficit in Metered Billing: Usage-based billing requires trusting the provider's internal analytics. In a zero-trust blockchain environment, consumption must be cryptographically verifiable — not merely claimed.

02  TARGET USERS & PERSONAS
	

Primary User Cohorts
The addressable market consists of three highly distinct user cohorts, each with fundamentally different interaction patterns and pain points. The protocol must serve all three natively without requiring separate integration work.


Cohort A: DAOs & Multi-Sig Treasuries
Persona: 'The DAO Ops Lead'
A contributor responsible for procuring enterprise tooling for a decentralized autonomous organization. They must coordinate purchase approvals through a 3-of-5 multi-sig wallet, cannot provide a personal credit card, and need auditability of all treasury expenditures on-chain.
	

Core Pain Points:
* Traditional SaaS platforms require a single human credit card owner, forcing convoluted reimbursement flows that break DAO governance models.
* Manually approving routine monthly subscription payments across 5+ signers imposes an exponential coordination burden.
* No audit trail of software spend exists on-chain, making treasury reporting opaque.


What They Need:
* A wallet-native checkout flow that accepts multi-sig authorization.
* Automated recurring payments that, once set up, do not require repeated multi-sig approval for each cycle.
* On-chain, auditable records of all subscription spend.


Cohort B: Tokenized Ecosystems & NFT Communities
Persona: 'The Web3 App Developer'
A developer building a token-gated analytics platform or community tool. They need to dynamically grant and revoke feature access based on real-time on-chain state — wallet balance, NFT ownership, governance token holdings.
	

Core Pain Points:
* Web2 feature flag tools (LaunchDarkly, Split.io) cannot read on-chain state natively.
* Developers must build custom, brittle middleware to bridge blockchain node data to centralized feature dashboards.
* Token-gating breaks whenever the middleware goes down, creating centralized failure points.


What They Need:
* A decentralized feature flag system where access conditions are defined on-chain and evaluated cryptographically.
* Drop-in React components for subscription checkout and feature gating.
* Real-time entitlement updates when a user's on-chain state changes (token transfer, NFT sale, etc.).


Cohort C: Autonomous AI Agents
Persona: 'The AI Agent Runtime'
A fully autonomous AI system that must procure computational resources, API access, and data feeds programmatically in real-time. It has no browser, no email address, no ability to complete a checkout form — and must negotiate and pay for fractional API usage at high frequency.
	

Core Pain Points:
* Traditional payment rails require KYC, human identity verification, and browser-based checkout — none of which are compatible with autonomous agents.
* High-frequency microtransactions for API calls are economically unviable on base-layer blockchains due to gas costs.
* Service providers cannot verifiably prove consumption amounts; agents must blindly trust billing claims.


What They Need:
* An HTTP-native payment standard (x402) that allows agents to evaluate cost and authorize payment programmatically.
* Off-chain consumption aggregation to avoid per-request gas costs.
* zk-SNARK verified billing proofs — cryptographic guarantees against overbilling.

03  TECHNICAL ARCHITECTURE
	

Architecture Overview
The protocol is divided into two primary subsystems — MEAP and ZKVUB — that share common infrastructure layers for identity, state management, and cross-chain interoperability. Both subsystems expose developer-facing SDKs and smart contract primitives.


Architecture Principle
Every component that can be decentralized must be. Centralized components are only permitted where cryptographic alternatives are not yet production-ready. All centralized components must have a documented decentralization roadmap.
	

Subsystem 1: MEAP — Modular Entitlement and Access Protocol
3.1.1 Smart Account Layer (ERC-7579)
MEAP's foundational innovation is replacing standard Externally Owned Accounts (EOAs) with ERC-7579 modular smart accounts. This is the architectural prerequisite for all automated billing functionality.


ERC-7579 Module Architecture:
* Validators: Cryptographic signature verification modules (e.g., ECDSA, multi-sig, passkey-based).
* Executors: Logic modules that can initiate transactions. The MEAP Autopay Executor is installed here.
* Fallback Handlers: Handle unknown function calls, enabling extensibility.
* Hooks: Pre- and post-execution logic for safety checks and rate limiting.


The Autopay Executor Module:
This is the core billing primitive. When installed by a user into their smart account, the Autopay Executor grants the SaaS provider's billing contract the authority to execute highly constrained pull transactions. The authorization parameters — max deduction per interval, approved token (USDC), approved merchant address — are cryptographically encoded at installation time. The user can revoke this module on-chain at any time, instantly terminating all future payment authority.

3.1.2 Entitlement State Layer (ERC-5643 + Tableland)
Once a payment is settled, the entitlement state must be recorded in a decentralized, verifiable manner. MEAP uses a two-layer approach:


Layer A — ERC-5643 Subscription NFT:
A time-constrained NFT is minted or updated upon successful payment. This NFT serves as the on-chain source of truth for the user's subscription status. It contains built-in functions for checking membership validity, triggering renewals, and managing expiration. The SubscriptionRegistry.sol contract extends ERC-5643 with additional logic for multi-tier plan management and cross-chain state references.


Layer B — Tableland Decentralized Relational Database:
Granular entitlement metadata (specific feature flags, API rate limits, tier-specific permissions, custom enterprise entitlements) cannot be stored cost-effectively on-chain. Tableland provides an ACID-compliant SQLite database where write access is governed by smart contracts. The SaaS provider executes SQL write operations to update a user's feature configuration, while the read access remains decentralized. The Tableland table schema is standardized by the MEAP protocol to ensure interoperability.

3.1.3 Access Control Layer (Lit Protocol)
The final layer of MEAP enforces cryptographic access control on the SaaS application's premium content and features. Instead of a server-side SDK checking a database, the application's premium payloads are encrypted using Lit Protocol, and decryption keys are only provisioned to clients who satisfy the on-chain Access Control Conditions (ACCs).


Access Control Condition Definition:
The SaaS provider defines ACCs using Lit Protocol's condition language. A minimal MEAP ACC checks: (1) that the client's wallet holds a valid, non-expired ERC-5643 NFT from the SubscriptionRegistry contract, and (2) that the wallet's Tableland record shows the specific feature flag requested is enabled for their plan tier. Both conditions are evaluated by the decentralized Lit Protocol node network — no centralized server is involved in the access decision.


Key Security Property
The Lit Protocol network uses Multi-Party Computation (MPC) and Trusted Execution Environments (TEEs) to distribute key management. No single Lit node holds the complete decryption key. A threshold of nodes must agree that the ACC is satisfied before a key share is provisioned — making it impossible for any single compromised node to grant unauthorized access.
	

Subsystem 2: ZKVUB — Zero-Knowledge Verifiable Usage Billing
3.2.1 x402 Machine Payment Layer
The ZKVUB subsystem begins at the HTTP layer. When any client (AI agent, programmatic API consumer) requests a metered resource, the server does not immediately fulfill the request. Instead, it returns an HTTP 402 Payment Required response formatted according to the x402 open standard.

The AI agent or client application parses this response, evaluates whether the cost is acceptable given its operational parameters, and if approved, constructs a signed payment payload and resubmits the request with an X-PAYMENT header. The Facilitator Node validates this payment, submits it on-chain, and the server grants access — all within the span of a single HTTP request-response cycle.


3.2.2 Off-Chain Aggregation Layer
For high-frequency API consumption (thousands of calls per hour by AI agents), executing one on-chain transaction per API call is economically unviable. ZKVUB solves this through off-chain aggregation:


* The client pre-funds a ZKVUB billing session by depositing stablecoins into a session vault smart contract.
* All API calls within the session are metered off-chain by the Facilitator Node, which records a signed consumption log for every request.
* The logs are cryptographically tied to the client's identity (wallet address) and the session ID.
* At configurable intervals (time-based or consumption-threshold-based), the SaaS provider's proving infrastructure aggregates the logs and generates a zk-SNARK proof.


3.2.3 Zero-Knowledge Proof Layer (zk-SNARK)
The zk-SNARK (Zero-Knowledge Succinct Non-Interactive Argument of Knowledge) is the cryptographic core of ZKVUB. It solves the trust deficit in usage-based billing by making consumption mathematically provable without exposing proprietary data.


What the Proof Attests:
* The exact number of API calls consumed in the billing window.
* The specific wallet address / agent identity that consumed them.
* That each call was a valid, authenticated request (signed consumption log).
* That no calls have been double-counted across billing windows.


What the Proof Does NOT Reveal:
* The content of any individual API request or response.
* The provider's internal pricing logic, algorithms, or data sources.
* Any personally identifiable information about the agent's operations.


Proof Generation Tooling
MVP implementation will use Groth16-based zk-SNARKs generated via the snarkjs library or Circom circuit compiler. The proving system will be upgradeable to zk-STARKs (Space and Time's Proof of SQL) in Phase 2 for improved trust assumptions (no trusted setup required).
	

3.2.4 On-Chain Settlement Layer
The ZKUsageVerifier.sol contract receives the zk-SNARK proof and executes settlement in a single atomic transaction:
4. Proof Verification: The verifier contract performs a lightweight mathematical check (pairing operations on elliptic curves) to confirm proof validity. This costs approximately 150,000-200,000 gas — far cheaper than re-executing all metered transactions individually.
5. Amount Calculation: Using the verified consumption count and the plan's rate schedule (stored in SubscriptionRegistry.sol), the contract calculates the exact settlement amount.
6. Fund Transfer: The contract interfaces with the client's session vault or authorized smart account and executes a precise stablecoin transfer to the provider's address.
7. Proof Nullifier: A unique nullifier is stored on-chain to prevent double-spending the same proof.
8. Event Emission: A BillingSettled event is emitted with full details for off-chain accounting systems.


Cross-Chain Interoperability Layer
3.3.1 General Message Passing (GMP)
A critical requirement of the protocol is that an entitlement purchased on one chain must be recognized by access control modules on other chains. MEAP implements this using General Message Passing (GMP) via two supported providers:


GMP Provider
	Mechanism
	Axelar Network
	Proof-of-stake validated message passing
	Chainlink CCIP
	Decentralized oracle-validated cross-chain messaging
	Optimism Superchain (Phase 3)
	Native interoperability for L2-to-L2
	Wormhole (Phase 3)
	Broad chain coverage for exotic L1s
	

When a subscription payment is made on Base (L2), the SubscriptionRegistry contract on Base emits a cross-chain message via the configured GMP provider. This message triggers an update to the MirrorRegistry contract on Ethereum mainnet, Polygon, and any other chains the SaaS provider has registered. The Lit Protocol ACCs are evaluated against the MirrorRegistry — ensuring access decisions are always based on the latest, cross-chain-synced entitlement state.

05  DEVELOPER SDKS & INTEGRATION COMPONENTS
	

SDK Architecture Principles
The protocol's complexity — modular accounts, zk-proofs, cross-chain messaging, threshold cryptography — must be entirely abstracted from the developer experience. The SDK surface area should feel as familiar as Stripe's JavaScript SDK: install, configure, drop in a component, and go.
Developer Experience Goal
A developer should be able to go from zero to a working Web3 subscription checkout in under 30 minutes. All cryptographic complexity happens behind SDK abstractions. The developer interacts with typed TypeScript interfaces, not Solidity ABIs or Lit Protocol condition syntax.

09  COMPLIANCE & ACCOUNTING FRAMEWORK
	

Revenue Recognition (ASC 606 / IFRS 15)
The protocol's on-chain metadata is specifically structured to support automated ASC 606 compliance:
* Subscription Revenue: Revenue from subscription NFTs must be amortized over the service period encoded in ERC-5643 expiresAt. The billing interval and per-period amount are immutably recorded on-chain.
* Usage Revenue: Revenue from ZKVUB settlements is recognized at the point of settlement transaction (when the ZKUsageVerifier.sol emits BillingSettled). The verified call count and per-call rate are on-chain inputs.
* Stablecoin Policy: Protocol enforces USDC-only (or provider-specified fiat-backed stablecoins) to eliminate FASB ASU 2023-08 fair value measurement complications from crypto asset volatility.


Tax Compliance Integrations
Integration Partner
	Scope
	Rain
	Automated crypto accounting and tax preparation
	Karat
	Web3 business banking and accounting
	Crypto.com Tax
	Transaction-level tax reporting
	Custom Web3 CPA Export
	Structured JSON export of all billing events
	

Data Privacy (GDPR / CCPA)
* No PII is stored on-chain. Wallet addresses are pseudonymous by design.
* Tableland entries contain only wallet addresses and entitlement state — no personal data.
* Optional zkProofer integration allows compliance verification without PII disclosure.
* The Facilitator Node processes x402 payment payloads and should be deployed by SaaS providers in their jurisdiction to comply with data residency requirements.


KYC / AML Framework
The protocol supports a tiered KYC framework that providers can opt into based on their regulatory requirements:
15. No KYC (Default): Open access for any wallet. Suitable for permissionless Web3 applications and AI agents.
16. ZK Credential (Optional): Humanity Protocol or similar zkProofer verifies the user passes a compliance check without revealing PII. Provider receives a boolean attestation only.
17. Full KYC (Enterprise): Off-chain KYC linked to wallet via verifiable credential. Provider manages the KYC process externally; the credential is cryptographically bound to the wallet for on-chain access decisions.

Glossary of Key Terms
Term
	Definition
	ERC-5643
	Ethereum token standard for subscription-based NFTs with built-in expiry and renewal logic
	ERC-7579
	Minimal standard for modular smart accounts that support installable plugin modules (Validators, Executors, Hooks)
	EOA
	Externally Owned Account — a standard crypto wallet controlled by a private key, incapable of autonomous execution
	ACC
	Access Control Condition — Lit Protocol's condition language for governing decryption key provisioning
	GMP
	General Message Passing — cross-chain communication protocol for sending arbitrary data between blockchains
	MPC
	Multi-Party Computation — cryptographic technique where a secret (e.g., decryption key) is split across multiple parties
	TEE
	Trusted Execution Environment — secure hardware enclave for processing sensitive data without external visibility
	zk-SNARK
	Zero-Knowledge Succinct Non-Interactive Argument of Knowledge — cryptographic proof of computation without revealing inputs
	Groth16
	A specific zk-SNARK proving system known for small proof size and fast verification (but requires trusted setup)
	x402
	Open internet payment standard leveraging HTTP 402 status code for machine-native, account-free payments
	Tableland
	Decentralized relational database network where table write access is governed by smart contracts
	Lit Protocol
	Decentralized key management and private compute network using MPC and TEEs for access control
	Facilitator Node
	MEAP's backend service that validates x402 payments, submits them on-chain, and gates API access
	Session Vault
	Smart contract holding pre-funded stablecoin balance for a ZKVUB billing session
	DID
	Decentralized Identifier — W3C standard for self-sovereign, cryptographically verifiable identity
	DAO
	Decentralized Autonomous Organization — an entity governed by smart contracts and token holder votes
	FASB ASU 2023-08
	US accounting standard requiring fair value measurement of crypto assets with changes in net income each reporting period
	ASC 606
	US GAAP revenue recognition standard — subscription revenue must be amortized over the service delivery period
